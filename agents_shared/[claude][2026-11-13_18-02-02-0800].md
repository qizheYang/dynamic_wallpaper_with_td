## Findings

| # | Sev | Finding | Proposed disposition |
|---|---|---|---|
| 1 | P1 | **Two M1/M2 gates cannot be measured without root.** The plan requires WindowServer physical footprint (the ≤64 MiB gate) and an "explicitly named" GPU method, but names none. Verified: non-root `footprint -p <WindowServer pid>` fails ("try as root?"), while it works on a user-owned process. The current harness has only global IOKit `Device Utilization %`, which cannot attribute GPU work. `powermetrics` offers `--show-process-gpu` (per-process GPU time) and GPU power samplers, but it also requires root. | M1 adds an opt-in privileged sampler mode. Only the samplers (`powermetrics --samplers tasks,gpu_power --show-process-gpu`, `footprint` for WindowServer) run under `sudo`; the probe never does. The user starts it. Name this as the GPU method in plan §8 and express the GPU gate as attributable GPU time (player + WindowServer increment, ms/s), not global %. If root sampling is declined, mark the WindowServer-memory and GPU gates **inconclusive by construction** now, and decide M2 on the measurable gates. |
| 2 | P2 | **The pilot baselines were probably contaminated, possibly by TouchDesigner itself.** `hardware.json` records 38–55% background GPU before testing. WindowServer swings across 39–53% between phases of the same run, so a ≤5 pp CPU gate cannot be resolved. On 2026-11-10 I saw an unrelated TD project open and cooking in real time at 60 fps. I cannot prove it was open during the runs; it is a plausible, project-specific contributor. | The M1 protocol lists apps that must be closed (TD explicitly) and records GPU-heavy process *names* per run. Before any comparison, require the idle-baseline WindowServer spread to be well below the budget difference. Fixing the display refresh rate instead of 120 Hz adaptive is worth testing as a control variable. |
| 3 | P2 | **M3 waits behind M1/M2 for no technical reason.** Plan §3 says the asset boundary is independent of the playback choice, and M2 already says the final asset is re-tested later. Meanwhile the biggest product uncertainty (does a TD loop look good and close seamlessly?) is untouched. | Run M3 in parallel with M1: `claude` takes the TD template and export (it has live TD access, see #7), `gpt6astra` takes the M1 harness. Because of #2, TD sessions and measurement sessions must not overlap in time on the same machine. |
| 4 | P2 | **The documented encode command produces wrong colors by default.** The command in `research/03-proposed-pipeline.md` §5 (`-pix_fmt yuv420p`, no matrix) converts RGB with **BT.601** and writes **no** color tags. Verified with FFmpeg 9.0.2/libx264 on a pure-red PNG: decoded Y/U/V = 81/90/240 (the BT.601 value), and `color_space/primaries/transfer/range = unknown`. Adding only `-colorspace/-color_primaries/-color_trc/-color_range` still left primaries and transfer untagged. AVFoundation typically interprets untagged HD as BT.709, so reds and greens shift. | Before the first M3 encode, replace the command with this verified form: `-vf 'scale=out_color_matrix=bt709:out_range=tv,setparams=colorspace=bt709:color_primaries=bt709:color_trc=bt709:range=tv'`. It gave Y/U/V 63/102/240 and all four tags `bt709`/`tv`. Whether `bt709` or sRGB is the right transfer tag still needs the planned test chart in a real AVPlayerLayer. Add an ffprobe tag check to M3 validation. |
| 5 | P2 | **The lock gate will probably end in narrowing the scope; a cheaper path exists.** I know of no documented "screen locked" notification. `NSWorkspace.sessionDidResignActiveNotification` covers fast user switching. The widely used `com.apple.screenIsLocked` distributed notification is undocumented, which the plan correctly forbids as a dependency. Hypothesis (not tested; I did not lock the screen): the lock screen covers the desktop-level window, so per-window occlusion should report it not visible. Lock, screensaver, and full-screen apps would then pause through the already-planned documented `occluded` reason. | Make the first step of the M1 lock spike: lock the screen and log `occlusionState` and `player_rate` for the wallpaper window. If it flips, restate the requirement as "not playing while locked" via occlusion, and keep `sessionInactiveOrLocked` for fast user switching. If it does not flip, continue with the plan's existing narrowing path. |
